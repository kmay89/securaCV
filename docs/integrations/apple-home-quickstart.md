# Apple Home quickstart — from nothing to a sensor in the Home app

Two lanes, both ending with your fleet in the Home app. Pick one:

| You have… | Go to | Time |
|---|---|---|
| An Apple TV or HomePod | [§1, the setup wizard](#1-run-the-wizard) | ~2 min |
| Home Assistant already running | [the HomeKit Bridge recipe](apple-home-homekit-bridge.md) | ~5 min, no new code |

Either way you need **one Apple TV or HomePod** signed into your Apple
Account. That is what makes it a Home Hub — without one, HomeKit accessories
work only while your phone is on the same Wi-Fi, and automations don't run at
all.

## 1) Run the wizard

<!-- BEGIN GENERATED: build -->
<!-- Generated by scripts/gen_apple_home_docs.py — do not edit by hand. -->
```sh
cargo build --release --features bridge-homekit-server --bin hap_bridge
```
<!-- END GENERATED: build -->

```sh
./target/release/hap_bridge setup
```

That is the whole install. The wizard:

1. **Looks for your Apple TVs and HomePods** over mDNS and tells you what it
   found. (Being on the network isn't the same as being signed in as a Home
   Hub — that's a setting only the Home app knows, so the wizard reports
   what it saw rather than declaring you ready.)
2. **Listens for your Canaries** on your MQTT broker and offers them by name,
   already title-cased — `porch-canary` becomes "Porch Canary", which you can
   overtype.
3. **Asks the one question that matters**: should Apple Home be told *what
   kind* of thing moved? Off unless you say yes.
4. **Asks how fast**, in plain language, because that dial is a privacy
   choice and not a speed setting.

Then it prints a **QR code in your terminal**. Open Home → **+** → **Add
Accessory**, point your phone at your screen, done.

It writes `hap.toml`, so from then on it's just:

```sh
./target/release/hap_bridge
```

> **iOS will say "uncertified accessory"** and offer **Add Anyway**. That's
> expected — this isn't an Apple-certified product, and every Homebridge and
> HomeSpan user sees the same prompt.

### If the QR won't scan

Your terminal's theme is fighting it. The default renderer paints its own
black-and-white background so this shouldn't happen, but if it does:

```sh
hap_bridge setup --qr light   # for a light-background terminal
hap_bridge setup --qr dark    # for a dark one
hap_bridge setup --qr off     # just print the code and type it
```

### Doing it without the wizard

Every answer is a flag, and `hap.toml` is a plain file you can write by hand:

```sh
hap_bridge --canary porch-canary="Porch Canary" \
           --canary garage-canary="Garage Canary" \
           --mqtt-host 192.168.1.10
```

> **Order matters.** The order of Canaries — flags or config file — fixes
> their HomeKit accessory ids, and controllers cache those. Reordering them
> after pairing makes the Home app read the wrong device. **Append** new
> Canaries to the end.

### No MQTT yet? Prove the pairing first

```sh
hap_bridge --canary test="Test Canary" --no-mqtt
```

The accessory pairs and publishes on the metronome; every signal simply
stays clear. Useful for separating "pairing is broken" from "events aren't
arriving," which otherwise look identical.

## 2) What you'll see

One accessory per Canary, with a tile for each *sensor* signal; the three
status signals have no tile of their own and ride along on every tile instead.

**Tile name in Home** is what Apple's Home app actually prints under the
accessory name — you'll see "Porch Canary — Person", not "Porch Canary —
Motion (person)". The **Signal** column is this project's own name for the
same thing, which is what you'll see in the SecuraCV apps and in
`hap_bridge --help`.

<!-- BEGIN GENERATED: signals -->
<!-- Generated by scripts/gen_apple_home_docs.py — do not edit by hand. -->
| Signal | Tile name in Home | Appears as | On by default |
|---|---|---|---|
| Motion | **Motion** | Motion sensor | yes |
| Occupancy | **Occupancy** | Occupancy sensor | yes |
| Contact | **Contact** | Contact sensor | yes |
| Tamper | — rides on each tile | Status on each sensor | **always** — cannot be turned off |
| Responding | — rides on each tile | Status on each sensor | yes |
| Low battery | — rides on each tile | Status on each sensor | yes |
| Motion (person) | **Person** | Motion sensor | **no** — you must ask for it |
| Motion (vehicle) | **Vehicle** | Motion sensor | **no** — you must ask for it |
| Motion (animal) | **Animal** | Motion sensor | **no** — you must ask for it |
| Motion (package) | **Package** | Motion sensor | **no** — you must ask for it |
<!-- END GENERATED: signals -->

Tamper is deliberately not disableable. A witness reporting that it was
interfered with must not be able to do so invisibly to a home you already
chose to publish into.

## 3) The tick is a privacy dial, not a performance knob

The bridge publishes on a metronome — on that cadence **whether or not
anything happened**. Constant rate, so the fact that a packet went out tells
an observer nothing.

<!-- BEGIN GENERATED: pacing -->
<!-- Generated by scripts/gen_apple_home_docs.py — do not edit by hand. -->
- **Default:** 1000 ms (1 s) — instant to a human, and nothing downstream can place an event more precisely than that.
- **Range:** 200 ms to 600000 ms. A value outside it is **refused, not clamped** — pacing is a privacy parameter, so being quietly overruled would be worse than an error.
- **Motion hold:** 10 ticks, so a momentary event stays visible long enough for an automation to see it.
<!-- END GENERATED: pacing -->

The wizard offers this as three plain choices. Coarsen it and external
timing blurs; shorten it and automations feel snappier.

## 4) Turning on the class-scoped signals

Off by default. They carry one extra word — the coarse object class — which
is the single sanctioned step past what a hardware PIR sensor would publish:

<!-- BEGIN GENERATED: classes -->
<!-- Generated by scripts/gen_apple_home_docs.py — do not edit by hand. -->
`motion_person`, `motion_vehicle`, `motion_animal`, `motion_package`
<!-- END GENERATED: classes -->

```sh
hap_bridge --enable-class motion_person
```

This is still not identity. There is no face, no plate, no name, no
re-identification, and no field in the vocabulary for any of them. It is
"a person-shaped thing moved," not "who."

Enabling one is logged, because it should never happen silently.

## 5) Keep the state file

```
hap_state.json   (mode 0600)
```

It holds the accessory's private key, its setup code, and every pairing.
`hap.toml` sits beside it and may hold your broker password, so it gets the
same treatment.

- **Back it up.** Losing it means every controller in the house must pair
  again from scratch.
- **Keep it private.** The bridge *refuses to start* if either file is
  readable by group or other, and tells you to `chmod 600` — it will not
  quietly fix the mode, because a key that has already been exposed should be
  treated as exposed.

## 6) When it doesn't work

| Symptom | Try |
|---|---|
| Bridge never appears in "Add Accessory" | Phone and bridge must be on the same subnet — mDNS does not cross VLANs. Check the host firewall allows UDP 5353 and TCP 51826. |
| The wizard found no Apple TV | Same reason, usually. It's a warning, not a blocker: pairing still works from a phone on the same network. |
| The wizard found no Canaries | Broker details, or the fleet hasn't published since it last started. Check with `mosquitto_sub -h <broker> -t 'securacv/+/status' -v`. You can always add them by hand. |
| "Accessory not found" after entering the code | Something else may be paired to it already. An accessory that is already paired refuses new pairings by design; delete it from the Home app first, or start from a fresh state file. |
| Paired, but every sensor is blank | Events are not arriving. Confirm the device ids in `hap.toml` match the MQTT topics exactly. |
| Occupancy never turns on | Presence rides in the retained `state` snapshot (`securacv/<id>/state`, field `presence`), not a `presence` topic. Confirm your firmware publishes it. |
| Worked, then stopped after a restart | The state path changed, so the bridge minted a new identity. Point it back at the original file. |
| Automations don't run when you're out | No Home Hub. An Apple TV or HomePod must be signed in and set as a hub. |
| Forgot the setup code | `hap_bridge code` prints it and the QR again. |

Run with `RUST_LOG=debug` for more.

## 7) What this never sends

- **No video.** Not here, not through HomeKit Secure Video. That decision and
  the triggers that would revisit it are recorded in
  [the design doc](../design/apple_home_integration.md) §2.
- **No identity, no zone, no timestamp, no count, no confidence.** The
  vocabulary has no field for any of them, so there is nothing to leak and no
  setting to get wrong.
- **Nothing inbound.** Signals are read-only by construction: Apple Home is
  an audience for witness state, never a control surface for it.

## 8) Honest status

The pairing transcript follows the HAP specification and is exercised
end-to-end by tests that drive it with an independently written controller,
plus a live check where an external process completed pair-setup M1→M2 over a
real socket. **That proves the wire format, not that Apple's controller
accepts it** — only pairing against a real Apple TV or HomePod settles that,
and this document will say so plainly until it has.

If you hit something this table doesn't cover, that is worth an issue: it is
the first time this lane has met real hardware.
