01 The idea in one breath

iPad doesn't get its own app. It gets the same one.

Everything you see in the Lab — the isometric room, the six-stage build line, the 3D device cards, the fix-it flows — is one static bundle: canary-local/. Plain HTML, CSS, JS, and committed WebAssembly. No build step, nothing to compile.

Tauri's job is to put a native window around that bundle on each operating system. On the Mac it's a macOS WebView; on iPad it's the iPadOS WebView. Same pixels, native frame. The config already points the app at the shared bundle:

02 Get it on iPad

The actual walkthrough

You do this on a Mac — iOS/iPadOS builds only come from Xcode's toolchain. Free Apple Developer tier is enough to run it in the iPad Simulator and side-load to your own iPad for 7 days; the $99/yr Program is only needed for TestFlight or the App Store.

  1. One-time setup on your Mac
    Install Xcode + Command Line Tools (this brings the iPad Simulator), sign in with your Apple ID, then add the Rust targets Tauri cross-compiles to:
    # the three iOS/iPadOS architectures Tauri needs
$ rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
  2. Install the app's dependencies
    From the desktop-lab folder — same package.json that builds the Mac and Linux installers:
    $ cd desktop-lab
$ npm install
  3. Generate the Xcode project
    This is the one command that makes iPad real. It reads tauri.conf.json + Cargo.toml and writes a full Xcode project into src-tauri/gen/apple/. You never hand-edit that folder — it's generated, and that's the whole trick to why it won't rot (§05).
    $ npm run ios:init      # → tauri ios init
  4. Run it in the iPad Simulator
    Build, boot a simulator, and launch. When prompted for a device, pick an iPad (e.g. iPad Pro 13") rather than an iPhone — that's all it takes to see the iPad layout. Live-reload is on, so edits to canary-local/ show up instantly.
    $ npm run ios:dev       # → tauri ios dev
# pick an iPad simulator, or plug in your own iPad and pick it
  5. Produce an installable build
    An unsigned .ipa for the Simulator needs nothing extra. For a signed build, set your Team ID and match --export-method to the destination — debugging (free Apple Development cert) for your own iPad, release-testing for TestFlight, app-store-connect for the App Store (the last two need the paid Program's Apple Distribution cert):
    $ npm run ios:build                       # unsigned .ipa

# signed to your own iPad (free Apple ID):
$ export APPLE_DEVELOPMENT_TEAM=XXXXXXXXXX   # your 10-char Team ID
$ npm run ios:build -- --export-method debugging
📓
Every command above already exists as a script in desktop-lab/package.json (ios:init, ios:dev, ios:build), and the full one-time checklist lives in desktop-lab/MOBILE.md. This guide is the narrated version of that doc. Just want to do it step by step without missing anything? Open the copy-paste runbook, desktop-lab/ipad-setup.html.
03 Why iPad feels right

The same shell, laid out for the room it's in

The Lab's navigation is adaptive by width, not by platform. One rule in the stylesheet decides everything: below 860px it collapses the sidebar into a bottom tab bar; above it, the sidebar stays. iPad is wide — so iPad gets the booklet-style sidebar, the Wikipedia-like index you wanted. iPhone is narrow, so it gets thumb-friendly tabs. No forked code; the layout just responds.

iPad · landscapesidebar
Full source-list sidebar — every bench one tap away, like a booklet you can flip.
iPhone · portraittab bar
Six build stages become six bottom tabs — reachable one-handed.

And because the stylesheet uses env(safe-area-inset-*), the tab bar clears the home indicator and the top bar clears the camera notch on its own — no per-device tuning. The iPad build inherits all of that for free the moment you wrap it.

04 How it works

Three mechanisms, and that's the whole machine

There's no fourth secret. iPad support is these three seams working together — each one already present in the repo today.

Mechanism 01 · the wrapper

The frontend is shared, not ported

Tauri points at canary-local/ and serves it inside the native WebView. The Rust entry point is already marked mobile-ready, so the same binary logic compiles to a desktop app or a mobile app depending on the target — no branch in your code.

lib.rs · #[cfg_attr(mobile, tauri::mobile_entry_point)]
Mechanism 02 · the seam

A capability layer that's honest per surface

The native shell exposes a small function the frontend can ask: what can this device actually do? Today it reports the shell it's running in; as native serial, BLE and mDNS land, the same call flips them on. The frontend reads this and shows only what's real — so USB flashing, which Apple blocks on iOS, is simply hidden on iPad and points to the desktop app instead of offering a button that can't work.

lib.rs · native_capabilities() → { serial, discovery, notifications }
Mechanism 03 · the source of truth

One manifest drives every surface

The benches, the room map, and the navigation all read from a single file. Add a bench there and it appears in the web Lab, the Mac app, and the iPad app at once — because they're the same frontend reading the same manifest. There is no iPad copy to keep in sync.

05 Why it self-heals, won't rot & works like magic

The parts that usually break are the parts we don't keep

iOS projects are notorious for bit-rot: Xcode changes its project format most years, and a hand-maintained .xcodeproj quietly stops opening. We sidestep the entire failure mode by never owning the fragile artifact in the first place.

🌱It won't rotgenerated, not authored

The Xcode project in gen/apple/ is derived from tauri.conf.json + Cargo.toml, never edited by hand. When a new Xcode ships, you don't patch anything — you delete the folder and run ios:init again, and it regenerates fresh against whatever toolchain you have now. The source of truth is config that doesn't age; the thing that ages is disposable.

🩹It self-healsdegrade, don't break

Every native power flows through the capability seam. If a capability isn't available — because it's iOS, or because Apple tightened a rule — the frontend reads false and hides that path rather than shipping a dead button. A new platform restriction becomes a one-line flag flip, and the UI reshapes itself around what's actually possible. Nothing is ever left pointing at a capability that vanished.

✨It works like magicone edit, four surfaces

Because iPad runs the identical canary-local/ bundle, a change to a bench, the room, or the nav ripples to web, Mac, Linux, and iPad in the same commit. You are never re-implementing the Lab for a new device — you're re-framing the one you already have. That's the whole illusion: there's less here than it looks like, which is exactly why it holds.

06 Real vs. your account

What's wired today, and what needs you

Straight about the seam: the scaffolding is all in the repo, but the first real build needs an Apple Developer account — signing and provisioning can't come from CI or this repo alone.

The split

✓ Already in the repo
  • ios:init/dev/build scripts in package.json
  • Mobile-ready Rust entry point & capability seam
  • Adaptive sidebar ↔ tab-bar layout with safe-area insets
  • MOBILE.md setup checklist
  • Gated CI workflow that no-ops until you enable it
→ Needs your Apple account
  • A Mac with Xcode + the iOS Simulator
  • Apple Developer sign-in (free tier to start)
  • Team ID for a signed device / TestFlight build
  • Repo variable ENABLE_IOS_BUILD=true + Apple secrets to turn CI on

The iPad CI job stays on manual dispatch and cleanly no-ops with a helpful message until those secrets exist — so it never blocks anything, and it's ready the day you wire up provisioning. Android is the same shape after this: tauri android init, same bundle, almost no new work.
